# 多井固井模型边界同步优化设计方案

## 1. 文档信息

- **文档版本**：1.0
- **创建日期**：2026-05-09
- **项目名称**：多井固井顶替效率模型边界同步优化
- **设计目标**：在不重写现有 2D 环空核心的前提下，先把六口井的地面注入 → 套管内传播 → 鞋口出流边界同步链条做准、做通、做成可复用接口。

---

## 2. 项目背景

### 2.1 当前代码基础

当前 `cemdisp/` 已经具备较完整的分层骨架：

1. `cemdisp/data/`：标准数据结构与逐井 loader；
2. `cemdisp/transport1d/casing_flow.py`：套管内 1D 体积推进求解；
3. `cemdisp/models2d/boundary_bridge.py`：鞋口边界桥接；
4. `cemdisp/models2d/annulus_d2dga.py`：环空 2D 顶替核心；
5. `cemdisp/diagnostics/quality_proxy.py` 与 `cemdisp/validation/`：后验解释与验证；
6. `cemdisp/runners/`：六口井运行入口。

现阶段最强的部分是环空 2D 核心；最需要优先收紧的部分，是**边界同步链条**：当前不同 runner 和 loader 对“地面施工程序如何变成鞋口入口边界”的表达仍不完全统一，而且部分井的施工阶段、鞋口滞后、代理流变和前置液口径差异较大。

### 2.2 本次优化的真实目标

本次优化不是直接追求“把最终效率调得更像现场”，而是先解决更上游的问题：

1. 地面注入顺序与鞋口边界是否同步；
2. 六口井是否都能通过同一套边界同步框架接入；
3. 各井资料缺项、代理值和回退规则是否被清楚记录；
4. 在边界同步变更后，旧入口假设与新入口假设对最终效率的影响是否可解释。

### 2.3 优先顺序

本次设计按以下优先顺序展开：

1. **鞋口时序同步**；
2. **并入各口井资料包的资料补强与 provenance 管理**；
3. **最终效率进一步贴场**。

这一定义意味着：第一阶段先解决入口边界问题，不把 CBL 反向校准、2D 主方程重写、1D 对流-弥散增强放进同一轮。

---

## 3. 设计目标与非目标

### 3.1 设计目标

本次设计的目标是建立一套**多井通用、分井可定制**的边界同步方案，使每口井都能从各自的施工程序出发，稳定生成鞋口处的标准边界时间线：

- `q(t)`：鞋口总排量；
- `vec(t)`：各流体或各相在鞋口处的体积分数；
- `stage(t)`：当前施工阶段标签；
- 关键阶段事件：到鞋时间、离鞋时间、切换时间、停泵/续泵影响；
- provenance 信息：该边界时间线依赖了哪些现场实测量、哪些邻井代理量、哪些暂定值。

### 3.2 非目标

本次设计明确不把下列事项作为第一阶段目标：

1. 不用 CBL 偏差直接回调 1D 或 2D 求解参数；
2. 不重写 `cemdisp/models2d/annulus_d2dga.py` 的主物理框架；
3. 不一开始就引入 1D 对流-弥散、ECD/压力耦合或 3D CFD；
4. 不把“当前资料缺项”固化成跨井分类体系的一部分；
5. 不把六口井当作完全同质样本使用同一套验收细则。

---

## 4. 总体设计原则

### 4.1 统一核心接口，分井定制策略

架构上仍然坚持通用框架，但不对六口井强行平铺一套规则。推荐原则如下：

1. **核心接口统一**：所有井最终都向 2D 环空模型输出同一种 `AnnulusInletState` 时间线；
2. **井级策略定制**：每口井都有自己的同步画像卡，描述这口井的几何口径、施工程序、相映射、鞋口滞后算法和验收项；
3. **资料状态并入各井资料包**：资料是否完整、哪些量是代理值、哪些量后续需要补数，都记录在每口井自己的 loader / provenance 中，而不再把“资料完整度”当作独立井类。

### 4.2 跨井只保留两条主分类线

#### A. 井段结构类型

- **双径/变径等效型**：呼101、呼探1井、呼探1-001井（HT1-001）
  - 特征：上段 `168.3mm`、下段 `139.7mm` 或类似双径结构；
  - 设计重点：等效井眼处理、鞋口滞后体积不能按单一内径粗算。

- **单径尾管型**：呼102、呼103、呼探1-002井（HT1-002）
  - 特征：目标求解井段以单一尾管口径为主；
  - 设计重点：施工程序真实性、阶段切换、局部代理参数和大肚子井段等附加影响。

#### B. 施工程序类型

- **简单双步型**：呼102
  - 典型特征：严格现场主作业口径下，以“尾浆 + 替浆”为主，前置液默认可缺省。

- **多前置液 + 多段替浆型**：呼101、呼探1井、呼探1-001井、呼探1-002井
  - 典型特征：平衡液/隔离液/领浆/尾浆/压塞液/轻泥浆/中置液/快替/慢替等多段流程并存。

- **多浆体系 + 多段替浆型**：呼103
  - 典型特征：平衡液、冲洗液、隔离液、领浆、中间浆、尾浆、压塞液和四段替浆同时存在，阶段更复杂。

### 4.3 每口井都需要同步画像卡

每口井都应维护一张同步画像卡，至少包含：

1. 井段结构口径；
2. 施工程序口径；
3. 鞋口滞后体积计算口径；
4. 流体相映射规则（如 lead/tail 是否分相，中间浆并入哪一相）；
5. 代理参数与回退规则；
6. 本井专属验收项。

同步画像卡不必独立成复杂新框架，也可以先由 loader 的结构化注释、常量定义和 provenance 记录承载，再逐步抽象。

## 5. 六口井的设计落点

### 5.1 呼101

- **结构特征**：双径/变径等效型；
- **程序特征**：平衡液 → 驱油隔离液 → 领浆 → 尾浆 → 后置液 → 轻泥浆 → 中置液 → 井浆快替/慢替；
- **设计重点**：
  - 52m³ 鞋口滞后口径需要保留；
  - lead / tail 分相要能继续支持；
  - 上段 `168.3mm` 与下段 `139.7mm` 的等效几何不能在边界同步时丢掉。

### 5.2 呼102

- **结构特征**：单径尾管型；
- **程序特征**：现场主作业严格模式下以“尾管水泥浆 + 替浆液”两步为主，可选邻井代理前置液；
- **设计重点**：
  - 边界同步要支持“严格现场模式”和“补充前置液模式”两种口径；
  - 当前水泥浆 `n/K` 与泥浆 `PV/YP` 为暂定值，必须在本井资料包中显式留痕；
  - 新同步入口要能和当前 legacy 对比边界做逐时差异对比。

### 5.3 呼103

- **结构特征**：单径尾管型，但上段内径与壁厚存在代理值；
- **程序特征**：平衡液 + 冲洗液 + 隔离液 + 领浆 + 中间浆 + 尾浆 + 压塞液 + 四段替浆；
- **设计重点**：
  - 要能表达比呼102更复杂的多流体序列；
  - 中间浆体积、部分几何参数属于代理值，必须并入本井资料记录；
  - 多段替浆排量切换应成为本井验收重点。

### 5.4 呼探1井

- **结构特征**：双径/变径等效型；
- **程序特征**：平衡液、隔离液、领浆、中间浆、尾浆、压塞液、轻泥浆、保护液、快替/慢替；
- **设计重点**：
  - 上段/下段双径与鞋口滞后体积需要分段累加；
  - lead / intermediate / tail 的相映射需要清晰；
  - 井斜、居中度等存在代理剖面，必须和本井资料一起管理。

### 5.5 呼探1-002井（HT1-002）

- **结构特征**：单径尾管型，带大肚子井段特征；
- **程序特征**：平衡液、隔离液、领浆、中间浆、尾浆、压塞液和多段替浆；
- **设计重点**：
  - 井径并非简单常量，需保留两段大肚子井段信息；
  - 近垂直井特征决定本井的边界同步与几何口径不能直接照搬斜井代理模式；
  - 中间保护液、替浆排量切换要能被时间线准确表达。

### 5.6 呼探1-001井（HT1-001）

- **结构特征**：双径/变径等效型；
- **程序特征**：多前置液 + 多浆体系 + 多段替浆；
- **设计重点**：
  - 上下段内径明确，鞋口滞后体积应按双径真实分段累加；
  - Spacer 在本井口径中已作为幂律流体，边界同步需要保留该差异；
  - 不能和呼探1井共用同一套几何与流体代理假设。

## 6. 模块职责设计

### 6.1 `cemdisp/data/pumping_schedule.py`

职责从“步骤列表”扩展为“可表达现场事件的施工程序对象”。

建议增强点：

1. 每步保留体积、排量、备注；
2. 允许显式表达排量切换、停泵/续泵、压塞液、后置液等现场事件；
3. 不强行要求所有井都具备秒级记录，但要能明确“这是按步骤同步，不是按连续现场曲线同步”。

### 6.2 `cemdisp/data/loaders/*.py`

loader 仍然是**唯一允许承载单井差异**的层。

职责包括：

1. 组织本井的 `WellSpec`、`FluidSpec`、`PumpingSchedule`、`ValidationData`；
2. 记录本井资料来源、代理值与回退口径；
3. 输出本井同步画像卡所需的结构化信息；
4. 不把单井硬编码扩散到 `transport1d`、`models2d` 和通用验证层。

### 6.3 `cemdisp/transport1d/casing_flow.py`

这是第一阶段的核心改造位。

建议职责：

1. 将地面施工程序推进到鞋口；
2. 对每一段流体输出到鞋时间、离鞋时间和鞋口阶段变化；
3. 在首版仍以体积滞后为主，但为后续 1D 对流-弥散升级预留接口；
4. 支持不同井的鞋口滞后体积口径，而不把这些口径写死在求解器内部。

### 6.4 `cemdisp/models2d/boundary_bridge.py`

bridge 应继续保持“薄桥接”。

职责包括：

1. 把 `PipeExitState` 标准化为 `AnnulusInletState`；
2. 处理 lead/tail 分相或 cement 单相映射；
3. 不在 bridge 中混入 2D 求解逻辑；
4. 不在 bridge 中反向推导施工程序。

### 6.5 `cemdisp/runners/*.py`

runner 是多井设计的检验现场。

建议增强点：

1. 每口井 runner 输出“旧入口假设 vs 新同步入口”的并排结果；
2. 导出关键时刻差值、阶段切换差值和最终效率差值；
3. 每口井各自保留自己的结果说明与资料口径说明。

### 6.6 `cemdisp/models2d/annulus_d2dga.py`

第一阶段原则上**不做主物理重写**。

本阶段只要求它稳定吃进更真实的入口边界，并让使用者能够判断：边界变化本身对最终效率有多大贡献。

## 7. 数据流设计

推荐数据流如下：

```text
现场资料
  ↓
逐井 loader 规范化
  ↓
WellSpec / FluidSpec / PumpingSchedule / ValidationData / 本井 provenance
  ↓
1D 套管内同步（surface → shoe）
  ↓
PipeExitState 时间线
  ↓
BoundaryBridge
  ↓
AnnulusInletState 时间线
  ↓
2D 环空求解
  ↓
最终效率 / 风险指标 / 对比输出
```

本阶段要特别强调两个控制点：

1. **上游真实性控制点**：loader 是否忠实表达了该井现场施工程序；
2. **边界解释控制点**：1D 到鞋时间线是否能解释 2D 结果变化，而不是把所有差异都归咎于 2D 模型。

---

## 8. 误差控制与 provenance 口径

### 8.1 基本原则

1. 允许使用代理值，但必须在本井资料包中显式标注；
2. 允许先按步骤同步，不伪装成连续现场曲线同步；
3. 不把 CBL 当成流体力学真值；
4. 不把当前缺项固化为跨井分类标签。

### 8.2 需要记录的代理信息

每口井至少记录：

- 几何代理：上段内径、等效井眼、壁厚、居中度剖面等；
- 流体代理：泥浆 `PV/YP`、水泥浆 `n/K`、前置液流变、邻井替代口径等；
- 程序代理：中间浆体积、前置液是否存在、多段替浆体积拆分等；
- 同步代理：鞋口滞后体积算法与其依据。

### 8.3 provenance 的角色

`fluid_provenance` 或后续更广义的 provenance 记录，不只是给报告看，而是要直接参与工程判断：

1. 某口井结果偏差大时，先看它哪些输入是代理值；
2. 某口井补齐资料后，可以局部替换 provenance 条目，而不重写整体架构；
3. 结果汇总中应明确区分“现场实测输入驱动的结果”和“代理值驱动的结果”。

---

## 9. 验收标准

### 9.1 跨井通用验收

所有六口井都需要满足：

1. 通过同一套边界同步主流程接入；
2. 能稳定生成鞋口出流时间线；
3. 能输出标准 `AnnulusInletState` 供 2D 求解器使用；
4. 代理值、回退规则和资料说明在本井资料中可追溯。

### 9.2 分井专属验收

#### 双径/变径等效型井

至少验证：

1. 鞋口滞后体积不是按单一内径粗算；
2. 变径位置不会把流体阶段切换顺序算乱；
3. lead / intermediate / tail 分相口径与本井 runner 输出一致。

#### 单径尾管型井

至少验证：

1. 多段替浆的排量切换顺序正确；
2. 简单双步井与复杂多段井都能走同一主流程；
3. 旧入口假设与新同步入口的差值能被明确导出。

#### 程序复杂井

至少验证：

1. 前置液、压塞液、后置液、中间浆等不会在边界同步中丢段；
2. runner 能说明每一段什么时候到鞋、什么时候离鞋；
3. 如果部分施工量是代理值，输出中会明确提醒。

### 9.3 第一阶段成功标准

当以下条件同时满足时，第一阶段可视为完成：

1. 六口井都能通过同一套边界同步主流程运行；
2. 每口井都有自己的同步画像卡和本井资料说明；
3. 至少能稳定导出“旧入口 vs 新入口”的关键差值摘要；
4. 使用者能够判断某口井结果的主要不确定性来自边界同步、资料代理，还是 2D 主模型本身。

---

## 10. 后续阶段建议

### 10.1 第二阶段：逐井资料补强

在第一阶段边界同步链条稳定后，优先补强各井的：

1. 前置液/隔离液/中间浆/压塞液真实施工量；
2. 水泥浆和泥浆实测流变；
3. 更准确的双径内径、壁厚、居中度和井斜剖面。

### 10.2 第三阶段：最终效率贴场优化

只有在入口边界足够可信之后，才进入：

1. 判断 2D 核心是否仍需增强；
2. 判断 1D 体积滞后是否要升级为 1D 对流-弥散；
3. 在保持 CBL 仅用于验证/解释的前提下，收敛最终效率口径。

---

## 11. 结论

本次设计把问题重新摆正为：

> 先做多井通用、分井定制的边界同步，再做资料补强，最后才谈最终效率贴场。

六口井不是一组同质样本，不应用同一份扁平验收模板处理；但它们也不应被拆成六套互不相干的模型。最合适的架构是：

- **统一核心接口**；
- **按井段结构和施工程序做跨井主分类**；
- **把资料状态并入每口井自己的资料包与 provenance**；
- **给每口井维护自己的同步画像卡与验收项**。

这套设计既能保持 `cemdisp` 的通用性，也能为后续逐井补资料和逐步提高最终效率可信度留出清晰路径。
